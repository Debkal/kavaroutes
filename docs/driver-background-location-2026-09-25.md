# Driver location while Google Maps is open — September 25, 2026

## Finding

The current `/driver` web client opens Google Maps in a new tab or app for navigation. That hides KavaRoutes. The [W3C Geolocation specification](https://www.w3.org/TR/geolocation/) says `watchPosition()` updates are delivered only to fully active, visible documents; hidden-document fixes are dropped. Therefore a site cannot request a persistent background location grant that makes its JavaScript GPS watcher keep running while Google Maps has the foreground. A browser may remember a geolocation *permission*, but that is separate from executing location updates in the background.

Chrome's newer [`<geolocation>` element](https://developer.chrome.com/blog/geolocation-html-element) improves the way the user grants and recovers permission and can watch position changes, but it is still a page element and does not change that visibility rule. [Persistent web storage](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist) protects stored data from eviction; it is not a GPS execution permission. [Background Sync](https://developer.mozilla.org/en-US/docs/Web/API/Background_Synchronization_API) can defer an already-created upload until network returns; it cannot acquire new locations while the page is hidden. These distinctions matter because the driver must navigate in Google Maps.

The browser can request a [screen wake lock](https://developer.mozilla.org/en-US/docs/Web/API/Screen_Wake_Lock_API) while KavaRoutes is visible. The local web change adds an explicit `Keep screen awake` button during an active shift, releases the lock when hidden or signed off, and reacquires on return. This is useful when Driver stays on screen. It does **not** keep GPS active during a Maps switch, and is not a production substitute for background tracking.

## Path that keeps the web interface

For an Android phone, ship a small installed companion whose foreground location service starts while Driver is visible, shows a persistent notification, and continues collecting through the Google Maps switch. The web page remains the driver interface; the companion owns GPS, local queueing and upload. Android documents the [`location` foreground service type](https://developer.android.com/develop/background-work/services/fgs/service-types) for long-running navigation/location-sharing work, with runtime location permissions and background-start restrictions. For iPhone, the installed companion needs Core Location background capability and an active [background location session](https://developer.apple.com/documentation/corelocation/handling-location-updates-in-the-background); the web page alone cannot create that session.

The repository has an Expo driver candidate with a native background task and notification, but its cloud mode is **synthetic** and explicitly sends no real GPS. It must not be presented as a ready live-tracking bridge. For both phone platforms, the production companion should display `app.kavaroutes.com/driver` as its web interface, open the existing Google Maps links in the Maps app, and run native GPS independently. The missing work is to bind the native task to the authenticated driver/shift with a short-lived, shift-scoped upload credential; queue real samples securely; upload through the existing idempotent `/location-batches` endpoint; stop on accepted shift closure or emergency stop; and show native tracking status to the web page. The web watcher must yield to native tracking in that installed app so the server does not receive two competing feeds for one shift.

Validate both an Android and an iPhone build on physical devices by starting a shift, opening Google Maps for 10–15 minutes, locking/unlocking, and checking Dispatch's last accepted fix and gap log. Browser-only fallback remains available when a companion is not installed, with explicit foreground-only status.
