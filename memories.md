# Current development rules

- Treat new Driver code and supporting web/API changes as production work. Include real authentication, tenant boundaries, bounded resource use, readable diagnostics, and verification of failure/recovery behavior. Do not leave temporary probes or synthetic fallback identities in the shipped Driver path.
- Pool reusable resources, share in-flight work, cache/memoize stable results, and batch requests when appropriate. Bound caches and queues, preserve failed-operation evidence, and measure third-party request counts.
- The current Driver app is `apps/driver-native`, displaying the dedicated web interface at `https://driver.kavaroutes.com/driver`. The historical `apps/driver` feasibility app is not the current release.
- Android builds use `npm run build:apk --workspace @kavaroutes/driver-native`. Bump `apps/driver-native/app.json` version and versionCode for changed distributed bytes. The script syncs the generated Android version fields, verifies metadata, names the APK `kararoutes_driverv<version-without-dots>.apk`, and copies identical bytes to `artifacts/mobile-builds` and `~/lanftp-received`. Never overwrite a distributed version with different bytes.
- Run Android 35 validation with `scripts/emulation/android35.sh` through the installed `~/emulation` environment. Keep temporary emulator test probes out of final packaged APKs. Distinguish emulator evidence from physical-phone/server receipt evidence.
- SQLCipher GPS queue operations must use a keyed connection. Expo's `withExclusiveTransactionAsync` opens another connection; applying a key only to the original connection is insufficient.
- Preserve existing user data and unrelated workspace files. Local commits are authorized; the user pushes Git. Existing VM deployment is authorized and should retain rollback evidence.
